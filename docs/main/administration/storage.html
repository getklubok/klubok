    Изображения и хранилище

    Изображения диаграмм хранятся вне PostgreSQL: оригинал и полноэкранный вариант лежат в блоб-хранилище (локальный каталог или S3), а маленький preview — в таблице images. Хранилище выбирается переменной STORAGE_PROVIDER, лимиты обработки — переменными IMAGE_*.

    Провайдеры

    Провайдер Значение Обязательные переменные
    Local STORAGE_PROVIDER=local STORAGE_LOCAL_PATH
    S3 STORAGE_PROVIDER=s3 STORAGE_S3_ENDPOINT, STORAGE_S3_REGION, STORAGE_S3_BUCKET

    STORAGE_PROVIDER по умолчанию local.

    Local

    export STORAGE_PROVIDER=local
export STORAGE_LOCAL_PATH=/storage
    • Каталог должен быть доступен на запись пользователю приложения (appuser). При старте приложение создаёт его при необходимости и делает пробную запись, поэтому без прав на запись оно не запустится.
    • В compose-файлах каталог /storage смонтирован из именованного volume klubok_storage, общего для blue и green: при переключении версии изображения остаются на месте.
    • При bind mount (- ./storage:/storage) права нужно выставить вручную — содержимое каталога на хосте принадлежит appuser внутри образа.
    • Бэкап: содержимое volume копируется вместе с дампом БД, иначе после восстановления preview будет, а оригиналов и полноэкранных вариантов не будет.

    S3

    export STORAGE_PROVIDER=s3
export STORAGE_S3_ENDPOINT="https://storage.yandexcloud.net"
export STORAGE_S3_REGION="ru-central1"
export STORAGE_S3_BUCKET="klubok"
export STORAGE_S3_ACCESS_KEY="..."
export STORAGE_S3_SECRET_KEY="..."
export STORAGE_S3_FORCE_PATH_STYLE=false
export STORAGE_S3_PREFIX=""
    • STORAGE_S3_ACCESS_KEY и STORAGE_S3_SECRET_KEY задаются только парой. Если оба пусты, используется стандартная цепочка credentials AWS SDK (роль инстанса, профиль, AWS_*).
    • STORAGE_S3_PREFIX добавляется к ключу объекта только на уровне провайдера, поэтому один бакет можно разделить между окружениями.
    • STORAGE_S3_FORCE_PATH_STYLE=true нужен для S3-совместимых хранилищ без virtual-hosted-style (MinIO и подобные).
    • Недоступность S3 не входит в readiness-пробу: приложение продолжает работать, а загрузка и выдача изображений отвечают 500.

    Лимиты изображений

    Переменная По умолчанию Назначение
    IMAGE_MAX_FILE_SIZE 2097152 Максимальный размер загружаемого файла, байт (2 МиБ)
    IMAGE_MAX_PIXELS 12000000 Максимальное число пикселей (ширина × высота)
    IMAGE_PREVIEW_MAX_SIDE_PX 250 Длинная сторона preview (хранится в БД)
    IMAGE_FULLSCREEN_MAX_SIDE_PX 2048 Длинная сторона полноэкранного варианта
    DIAGRAM_MAX_IMAGE_SHAPES 50 Максимальное количество Image-элементов в диаграмме

    Все значения должны быть положительными, иначе приложение не запустится. Принимаются только PNG и JPEG: формат определяется по содержимому файла, а не по расширению или заголовку запроса. GIF, WebP и SVG отклоняются с кодом 400, превышение размера файла — 413.

    DIAGRAM_MAX_IMAGE_SHAPES ограничивает число Image-элементов в одной диаграмме. Клиент проверяет лимит до загрузки файла и показывает предупреждение; при обходе клиента сервер отклоняет upsert Image-элемента с кодом 400. Перенос существующего элемента лимит не расходует, клонирование и JSON-импорт диаграмм лимит не проверяют.

    Лимит размера тела запроса

    Общего лимита на тело запроса в приложении нет. Фактический предел задаёт nginx — client_max_body_size 10m в deploy/nginx.conf. Multipart-разбор (ParseMultipartForm) держит в памяти до 32 МиБ и сбрасывает остаток во временные файлы, поэтому запрос заметно больше IMAGE_MAX_FILE_SIZE сначала полностью осядет в tmpfs/диске контейнера, и только потом счётчик байт вернёт 413.

    Практические следствия:

    • Держите client_max_body_size в nginx ненамного выше IMAGE_MAX_FILE_SIZE: 10m при лимите файла 2 МиБ — это запас на multipart-обёртку, а не приглашение загружать десятимегабайтные файлы.
    • Если IMAGE_MAX_FILE_SIZE поднимается, значение в nginx нужно поднять вместе с ним и наоборот.
    • Временные файлы multipart живут в каталоге временных файлов контейнера; при большом потоке загрузок стоит следить за свободным местом.

    Свёртывание и удаление

    Оригинал и полноэкранный вариант адресуются по хешу содержимого, поэтому повторная загрузка того же файла переиспользует уже лежащие блобы, а удаление изображения или диаграммы ставит блобы в очередь очистки после коммита транзакции.

    Очистка выполняется в процессе приложения: очередь ограничена 256 задачами, при переполнении задача теряется с предупреждением в логе. Потерянная задача оставляет файл в хранилище (orphan-блоб), но не ломает диаграмму — ссылка в БД уже удалена.

    Note

    Блокировка «не удалить блоб, который только что загрузили» работает внутри одного процесса. Развёртывание однорепличное (blue/green переключается целиком), поэтому этого достаточно; при переходе на несколько реплик очистку нужно переводить на advisory lock в PostgreSQL.
